# AutoMem recall-strategy evaluation — 2026-04-17

**Methodology:** 78-memory synthetic corpus (3 fake projects + preferences + noise) seeded into local Docker AutoMem stack. Real OpenAI embeddings. 10 session-start scenarios with known expected hits. Compared 12 ruleset variants across ~120 total runs. All experiments live in `automem-evals/`; nothing committed to `mcp-automem`.

## TL;DR

1. **The bare-tag 1M template (version 2.0.0) is empirically optimal** on this corpus — 24/24 expected hits vs baseline 14/24 in Phase 2+3 scenarios (Phase 1 tied at 20/20 for both once limit is bumped to 20).

2. **No single knob accounts for the win — they compound.** `+limit` alone adds 2 hits. `+time_query` alone is net neutral (gains old-memory scenarios, loses displaced recent ones under limit=10). `+auto_decompose` alone adds 0 on focused queries. Only **limit + time_query together** unlock the full 10-hit gain.

3. **`expand_relations` is non-functional under tag-gated queries.** `expanded_count: 0` every time `tags: [<slug>]` is set. Without the tag gate, expansion fires (expanded_count: 2) but the ungated baseline loses more ground to noise than expansion recovers. Net: **expand_relations adds 0 hits in every configuration we tested**, even with a purpose-built 11-edge association graph.

4. **Dropping the tag gate is a disaster** (-5 hits vs baseline). The project slug is load-bearing. Tag gating is not a luxury — it's what makes Phase 2 work.

5. **Infrastructure:** embedding snapshot + fast reseed now working. Teardown→reseed cycle went from ~40s (real API calls) to ~38s wallclock dominated by server enrichment (embedding storage takes 0.4s). Reseed costs $0 in embedding API.

## Corpus structure

- **Total memories**: 78
- **Preferences** (bare `preference` tag): 20
- **Project-scoped** (bare slug tag): tensor-pipeline 23, dashboard-app 14, old-service 13
- **Cross-project noise** (unmapped): 8
- **Age spread**: 51 in 0–30d, 13 in 31–60d, 7 in 61–90d, 7 in 91+d
- **Embeddings**: OpenAI 1024-dim, snapshotted to `corpus_v1.embedded.jsonl` (1.1 MB)
- **Associations**: 11 edges (8 within-scope + 3 cross-boundary: EXEMPLIFIES, DERIVED_FROM, REINFORCES)

## Experiment 1 — baseline_v1 vs bare_tag_1m_v2

10 scenarios across Phase 1/2/3. Detailed table in `20260417-230940-comparison.md`.

| Metric | baseline_v1 | bare_tag_1m_v2 |
|---|---|---|
| Total expected hits found | 24 / 44 | 44 / 44 |
| Scenarios with any hit | 8 / 10 | 10 / 10 |
| Scenarios fully recovered | 3 / 10 | 10 / 10 |

- Clear wins driven by **limit** and **time_query** independently. Clear compounding when both bumped.
- One P@5 regression on SS-TP-AUTH (0.75 → 0.60): wider net pulls more near-neighbors into top-5. With Opus 4.7's 1M context this is the right trade.

## Experiment 3 — expand_relations investigation

Designed 3 cross-boundary associations to test whether expansion surfaces memories that lack the scoped tag:

- `TP-RATE-fix` —[EXEMPLIFIES s=0.8]→ "Generic note: rate limiters should use token-bucket…"
- `TP-AUTH-fix` —[DERIVED_FROM s=0.75]→ "Generic auth note: prefer short-lived access tokens…"
- `TP-MEM-milestone` —[REINFORCES s=0.7]→ "Cross-project pattern: structured logging…"

Ran 3 expansion-target scenarios under 4 rulesets:

| Scenario (project: tensor-pipeline) | v2 (gated) | v2 no-gate | v2 no-gate + expand | v2 + expand |
|---|---|---|---|---|
| EXP-TP-RATE | 1/2 | 0/2 | 0/2 | 1/2 |
| EXP-TP-AUTH-WITH-GENERIC | 4/6 | 1/6 | 1/6 | 4/6 |
| EXP-TP-OBSERVABILITY | 1/2 | 0/2 | 0/2 | 1/2 |

**Cross-boundary memories (`CROSS-*`) never surfaced in any config.** Raw probing confirmed:

```
tags=tensor-pipeline + expand_relations=true → expanded_count: 0, seed_count: 23
no tags          + expand_relations=true → expanded_count: 2, seed_count: 30
```

**The tag gate blocks expansion targets.** So `expand_relations` is only live when the caller drops the tag gate — and in that mode, our 2-phase scheme underperforms (no-gate + multi-query suffix becomes too noisy).

The `.relations[]` metadata IS attached per-seed-result (we saw the correct EXEMPLIFIES edges in responses), so the graph is visible to the caller — but the connected memories are not promoted into the top-level `results[]` array. A client could walk these manually, but the automatic `expand_relations` promotion is effectively disabled whenever tag-gating is used.

**Finding for the AutoMem server repo:** consider whether expansion targets should bypass the tag filter. The graph edge is the explicit relevance signal; filtering it through a tag gate defeats the purpose.

## Experiment 4 — client-side expansion (prototype)

Since the server ships relations inline (`.results[].relations[]` contains full memory content) even when it refuses to promote them, I prototyped a 50-line client-side walker that runs AFTER the normal recall, inspects each result's relations, and merges high-strength edges (≥0.6, authorable types only) into the result set.

Run against the same EXP-TP-* scenarios using **identical v2 ruleset params** as the server-side test:

| Scenario | v2 alone | v2 + client-expand | added |
|---|---|---|---|
| EXP-TP-RATE | 1 / 2 | **2 / 2** | +1 (CROSS-RATE via EXEMPLIFIES) |
| EXP-TP-AUTH-WITH-GENERIC | 4 / 6 | **5 / 6** | +1 (CROSS-AUTH via DERIVED_FROM) |
| EXP-TP-OBSERVABILITY | 1 / 2 | **2 / 2** | +1 (CROSS-LOG via REINFORCES) |

Three for three. Every cross-boundary memory surfaced, with scores in a reasonable band (~0.25–0.48 via 0.9× hop decay of the seed score).

**This is a viable MCP-client feature.** `mcp-automem`'s `recall_memory` tool could expose a `client_expand` flag; if set, after receiving the server response it walks relations, filters by strength / edge-type, and merges. No server change required. The graph is already shipped in the response envelope.

Prototype at `automem-evals/runners/client_side_expand.py`. ~60 lines. No external dependencies.

**Caveat observed when running on the non-expansion-targeted scenarios:** the prototype's synthetic score formula (`seed_score * 0.9`) can promote relation targets above primary hits when the seed's score is high. On Phase 1 (preferences), this surfaced a pattern memory connected to a preference with score 0.830 — higher than many real preferences. A production client-expand feature should apply edge-strength weighting (`seed_score * edge_strength * hop_decay`) and ideally remain phase-aware (don't expand preferences to non-preferences). The prototype is enough to validate that the mechanism works — the scoring needs one more pass before it's ready to ship.

## What to do with this data

### For `mcp-automem/templates/` (the branch `feat/bare-tag-recall-strategy`)

- **Keep the current v2 template as-is.** Empirically optimal on the test corpus. No change needed.
- **Consider removing the reference to `expand_relations` in `CLAUDE_MD_MEMORY_RULES.md`** if it's currently recommended anywhere — it's a no-op under normal tag-gated recall.
- **Do NOT lower the `tags: [<slug>]` gate in Phase 2.** Confirmed load-bearing.

### For the AutoMem server repo (out of scope here)

Two server-side changes worth considering, in priority order:

1. **Expansion should bypass the tag filter.** A memory reached via a typed association has the graph edge as its relevance signal; re-applying the tag gate on expansion targets eliminates the feature's value. Issue #97 §D already documents this as a no-op; now we've confirmed the cause.
2. **Silent store-failure mode (Issue #97 §A)** didn't reproduce locally in this run — every seed POST returned a memory_id and each memory came back in recall. Worth keeping the local stack around for repro attempts when the production case next appears.

### For `automem-evals` (this repo)

The scaffolding built today is portable:

- `rulesets/*.json` — 12 rulesets, JSON-pluggable
- `scenarios/*.json` — 2 scenario suites (session-start, graph-expansion), extensible
- `scripts/{generate,seed,snapshot,seed_from_snapshot,seed_associations}_corpus.py` — full lifecycle
- `runners/compare_rulesets.py` — matrix runner, handles any N×M combination
- `data/seed_memories/corpus_v1.embedded.jsonl` — 78 memories with 1024-dim vectors, reseedable in 0.4s

Natural next steps:
- **Agent-matrix dimension** — wrap the runner so a "ruleset" can include not just recall parameters but an agent runner (Claude Code vs Codex vs Cursor). The recall comparison is unchanged; what differs is how the agent consumes the recalled context.
- **Client-side expansion as a mcp-automem feature** — Experiment 4 below shows this works. Promoting it from prototype to a `recall_memory` flag in the MCP client would be a small change and would unlock graph-expansion value that's currently blocked server-side.
- **Negative-control scenarios** — the current 10 scenarios are all positive ("did we find the hit"). Add scenarios where the correct answer is "nothing relevant" to measure over-retrieval.
