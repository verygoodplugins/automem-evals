## New findings from v2

### 1. Slug collision is real but less severe than I expected

The `video` project deliberately collides with video-content marketing / video-generation research memories (4 noise memories tagged `video` that aren't about the service). With `tags: ["video"]` the seed pool is 54 memories (50 project + 4 noise).

On `SS-VID-SLUG-COLLISION` query "video player and transcoding infrastructure":
- Baseline top-3: all project memories (DRM bug, HLS milestone, storage context).
- Bare_tag_1m top-5 P@5=0.80, 5/5 expected hits, first-hit rank 1.

**The semantic query was specific enough to outscore noise even under collision.** Content-marketing memories about "video podcasts" and "content strategy" did not surface high.

**Caveat:** a less-specific query like "video project plans" might collapse to noise. Worth testing with a deliberately-ambiguous query. The slug-collision rule in CLAUDE.md is still correct guidance, but the practical impact depends on query specificity.

### 2. Old-service sunset still misses under both schemes

`SS-OS-SUNSET-V2` returned 0/4 under both baseline and v2. The `old-service` memories are deliberately aged to 60-180+ days. Even the 90-day window catches none.

**Implication:** projects that are mostly-dormant need either (a) a longer `time_query` like "last 180 days" or (b) no time window at all. Worth a documentation note — or a template addition for a "long-running project" Phase 2 variant.

### 3. Phase 1 scales correctly

50 preferences divided across 13 scopes means the corpus has 43 expected Phase 1 hits (some scopes have 1 memory, some have 6). Limit=10 catches ~10, limit=20 catches 20. Linear. No surprises — the rank ordering is by importance + recency, so the highest-importance prefs are at the top in both cases. 20 is more than enough for practical recall; limit=30 or 50 adds little beyond diminishing returns.

### 4. Negative control holds

`SS-NEGATIVE-CONTROL` — query about Kubernetes/Istio/Helm (all absent from corpus) — returned 5 tensor-pipeline memories in top-5 (neither scheme gated by "is this actually about the query"). Both schemes exhibit the same over-retrieval. Scoring at 0/0 for both since the expected tag was nonexistent.

**Implication:** the recall schemes don't reject off-topic queries. A follow-up query relevance floor (like `min_score: 0.5`) would be useful. This is arguably what the server's `adaptive floor` in issue #128 is meant to address.

## What this means for the mcp-automem template

**No change from the v1 decision.** The bare_tag_1m_v2 template stays. Two minor additions worth considering in a follow-up:

1. **Document "stale project" variant.** When querying a project that's mostly dormant, relax `time_query` to "last 180 days" or drop it. Simple one-line guidance.
2. **Note the slug-collision threshold.** The CLAUDE.md rule is still correct (`video` ✗, `streamdeck-mcp` ✓), but actually validated: specific semantic queries mitigate the collision. If a project has a generic slug AND expects generic queries, flag that pair as risky.
